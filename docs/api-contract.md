## 1. Problem Schema

Source: `src/models/problem.model.js`, `src/services/problem.service.js`, `src/repositories/problem.repository.js`

| Field | Type | Required | Enums / Format | Default | Validation & Logic Rules |
|---|---|---|---|---|---|
| `_id` | `string` (ObjectId) | Read-only | 24-hex char MongoDB ObjectId | Auto-generated | Generated by MongoDB. |
| `title` | `string` | **Yes** | Non-empty string | None | Validated in service (`!title` throws `BadRequestError(400)`). Uniqueness enforced in service before creation (`getProblemByTitle` throws `ConflictError(409)`). |
| `description` | `string` | **Yes** | Markdown text | None | Validated in service (`!description` throws `BadRequestError(400)`). Automatically sanitized via `sanitizeMarkdownContent`: converted to HTML with `marked`, sanitized with `sanitize-html` (allowed default tags + `img`), and converted back to markdown via `turndown`. |
| `difficulty` | `string` | **Yes** (schema) | `'easy'`, `'medium'`, `'hard'` | `'easy'` | Mongoose enum check (`'easy' \| 'medium' \| 'hard'`). If missing on creation, defaults to `'easy'`. |
| `testCases` | `Array<{ input: string, output: string }>` | Optional | Array of test case objects | `[]` | Repository defaults to `problemData.testCases || []`. In schema, each item requires `{ input: string, output: string }`. |
| `editorial` | `string` | Optional | Markdown / text | None (`undefined`) | Optional explanatory text/solution notes. |
| `__v` | `number` | Read-only | Integer | `0` | Mongoose internal version key. |

### Schema Absences (Explicitly NOT in the database)
- **NO `tags` field**: Not present in the Mongoose schema or service.
- **NO `timestamps`**: No `createdAt` or `updatedAt` (schema does not enable `{ timestamps: true }`).
- **NO `acceptanceRate` or `solveCount`**: No stats tracking exists.
- **NO `author` / `user`**: No user or authentication model exists.

## 2. API Endpoints & Response Envelopes

### Base URL: `http://localhost:3001`

### 2.1 Health Check: `GET /ping`
- **Route definition**: `app.get('/ping', ...)` in `src/index.js`
- **Success Status**: `200 OK`
- **Response Shape**:
  ```json
  {
    "message": "Problem service is alive"
  }
  ```
- *Note:* Does not use the standard `{ success, data, error }` wrapper.

### 2.2 Controller Ping: `GET /api/v1/problems/ping`
- **Route definition**: `problemRouter.get('/ping', ...)` in `src/routes/v1/problems.routes.js`
- **Success Status**: `200 OK`
- **Response Shape**:
  ```json
  {
    "message": "ping controller is up"
  }
  ```

## 3. CORS Middleware Status

- **Status**: **NOT PRESENT**.
- In `src/app.js`, Express only mounts `express.json()`, `express.urlencoded()`, `express.text()`, `express.raw()`, `apiRouter`, and `errorHandler`. There is no `cors` package installed or registered as middleware.
- **Frontend Impact**: Any browser request directly from `http://localhost:5173` to `http://localhost:3001` will be blocked by standard browser CORS policies.
- **Remediation**: The frontend must use a reverse proxy during development via Vite's `server.proxy` forwarding `/api` and `/ping` to `http://localhost:3001`. The frontend API client must use relative URLs (`/api/...`, `/ping`) by default in development.

## 4. Code vs. Documentation Discrepancies

1. **`validators` Directory**:
   - *README*: Lists `src/validators/index.js # Validation middleware`.
   - *Actual Code*: `src/validators/` exists but is completely empty. Validations are executed imperatively in `src/services/problem.service.js` and declarative Mongoose schema constraints.
2. **Key name in `GET /problems`**:
   - *Expected standard*: `{ success: true, message: "...", error: {}, data: [...] }`.
   - *Actual Code*: Line 71 in `src/controllers/problem.controller.js` outputs `err: {}` instead of `error: {}`. The frontend envelope parser must support both `error` and `err`.
3. **Health Check `/ping`**:
   - *README*: Mentions `GET /ping` under Health Check.
   - *Actual Code*: Defined directly on `app` in `src/index.js` (not in `src/app.js`), returning `{ "message": "Problem service is alive" }` rather than the standardized API envelope.
4. **No Tags, Timestamps, or User Stats**:
   - *Assumption/UI Ideas*: Practice platforms often show tags, acceptance rate, creation date.
   - *Actual Code*: The schema contains no `tags`, `createdAt`, `updatedAt`, or stats. The frontend index will therefore support search by title and filter/sort by `difficulty` only, with clear design accommodation for future fields.
